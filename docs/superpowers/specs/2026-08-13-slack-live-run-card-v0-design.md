# Slack Live Agent Run Card v0 Design

**Date:** 2026-08-13
**Status:** Approved in conversation; awaiting written-spec review

## Goal

Give Slack participants immediate, useful visibility after they mention `@codevil`. Each Codevil Agent Run started from a linked Slack thread gets one native Slack card that updates in place while the agent works. At the end of the turn, Codevil finalizes the card and then posts the existing full agent response beneath it.

This is a deliberately narrow v0. It should make the real workflow observable quickly, preserve the existing Slack integration boundaries, and leave room to iterate from actual use.

## User Experience

### One card per Agent Run

Each `run_id` owns one live card in the linked Slack thread. A later tagged request in the same thread starts a new Agent Run and therefore creates a new card. The card is not shared across the whole Codevil Session.

Immediately after `agent_run_started`, Codevil posts the card with:

- a deterministic title derived from the explicit request;
- `in_progress` status;
- the current phase, initially “Starting”; and
- an **Open session** link.

The title is presentation-only, bounded to Slack's field limits, and is not generated by another model call.

### Curated live activity

While the run is active, Codevil updates the same card with:

- the current phase, such as preparing, investigating, changing code, verifying, or publishing;
- a concise user-visible status when Codevil emits one; and
- the latest meaningful actions, capped at eight entries.

Meaningful actions include safe summaries of repository searches, file reads, edits, tests, builds, commits, and pull-request publication. Codevil does not copy raw tool arguments, unrestricted commands, complete tool output, secrets, credentials, environment values, or hidden model reasoning into Slack.

The v0 does not publish `message_update` thinking deltas verbatim. It derives the card from explicit lifecycle/status events and a whitelist of sanitized tool-action categories.

### Questions and approvals

When a run needs a question answered or a plan approved, the card remains present and changes its detail to “Waiting for input.” Slack's `task_card` status remains `in_progress`, because the block does not define a separate waiting status.

The existing interactive question message and plan-approval notice remain separate messages. This preserves their controls, attribution, race handling, and full content. When the question is answered or execution is approved, the card resumes normal progress updates.

### Successful completion

At the end of a successful turn, Codevil performs these operations in order:

1. Update the live card to `complete` with a concise outcome.
2. Add a direct **View pull request** link when `agent_run_completed.pr_url` exists.
3. Retain **Open session** for the full Codevil timeline, activity, and diff context.
4. Post the existing full agent response as a separate Slack message immediately after the finalized card.

Long final responses continue to use the existing safe chunking behavior. The card does not replace or truncate the final answer.

### Failure

When an Agent Run fails, Codevil updates the card to `error` with a bounded, user-safe failure reason and **Open session**. It does not also post the existing duplicate run-failure notice unless no card could be created.

## Chosen Slack Mechanism

The v0 uses a native Block Kit [`task_card`](https://docs.slack.dev/reference/block-kit/blocks/task-card-block/) sent with `chat.postMessage` and replaced in place with `chat.update`.

This is preferred over `chat.startStream`, `chat.appendStream`, and `chat.stopStream` for v0 because Codevil is presenting a current run snapshot rather than streaming the final answer token by token. Replacing a complete snapshot is easier to retry, deduplicate, and reconstruct after a Worker restart. It also builds on Codevil's existing `postSlackMessage` and `updateSlackMessage` client helpers.

The streaming APIs remain a possible later enhancement if Codevil chooses to stream final answer prose in Slack.

The rendered Slack message contains:

- a top-level accessible fallback `text` value;
- one `task_card` block containing status and curated activity;
- URL source elements for **Open session** and, when available, **View pull request**; and
- a new unique `block_id` for each revision, as required for updated Block Kit messages.

No new Slack scopes are required. The existing `chat:write` scope covers posting and updating the card.

## Architecture

### Provider-neutral projection

Add an `ExternalRunPresentation` projection that is independent of Slack block shapes. It consumes Codevil's canonical, already-redacted event stream and produces a bounded snapshot:

```ts
interface ExternalRunPresentation {
  runId: string;
  title: string;
  status: "in_progress" | "complete" | "error";
  phase: string;
  summary?: string;
  actions: Array<{
    id: string;
    label: string;
    status: "in_progress" | "complete" | "error";
  }>;
  waitingFor?: "question" | "approval";
  prUrl?: string;
}
```

The Slack adapter translates this projection to `task_card`. Provider-specific message IDs and rendering remain outside the core Session projection.

### Durable ownership and serialized delivery

The existing Session Durable Object owns live-card coordination because it already serializes the Agent Run and stores the canonical event log. It maintains a single-flight outbound flush per Session:

1. `appendAndBroadcast` stores the validated, redacted event and receives its cursor.
2. The presentation projector records that cursor as pending.
3. If no flush is running, the Durable Object starts one through `ctx.waitUntil`.
4. The flush reads the newest complete run projection and writes one Slack snapshot.
5. If more relevant events arrived during the write, the loop renders the newest state again before ending.

This prevents an older `chat.update` request from completing after and overwriting a newer card.

### Durable presentation state

Add a per-Session Durable Object SQLite table for external run presentations. A row contains:

```text
run_id
provider
external_message_id          -- Slack message timestamp after creation
presentation_status
last_projected_cursor
last_delivered_cursor
last_render_fingerprint
pending_final_response_cursor
next_retry_at
created_at
updated_at
```

The canonical event log remains the source of presentation content. The row stores delivery coordination state, not another unbounded copy of the run transcript.

On Durable Object startup, a row whose projected cursor is newer than its delivered cursor is pending work. The coordinator schedules a retry through the Orchestrator's alarm path. `armNextAlarm` includes the earliest presentation retry alongside the existing provisioning, timeout, reconnect, and snapshot deadlines. The alarm handler drains due presentation work before any terminal-Session early return, so a card can still recover after its Session stops. This avoids adding a D1 migration and avoids competing directly for Cloudflare's single Durable Object alarm.

The existing D1 `external_session_links` table remains the source for the destination provider, channel, and thread. The live-card table does not move Slack identifiers into core Session metadata.

## Event Mapping

The v0 projector handles these event groups:

| Event | Presentation effect |
| --- | --- |
| `agent_run_started` | Create the run projection and post its card immediately |
| `phase` and safe `status` | Update the current phase or concise summary |
| `agent_event.tool_execution_start` | Add or mark a sanitized action `in_progress` |
| `agent_event.tool_execution_end` | Mark the matching action `complete` or `error` |
| `question_raised` | Show “Waiting for input”; keep question controls separate |
| `question_answered` | Clear the waiting marker and resume updates |
| `approval_requested` | Show “Waiting for approval”; keep plan content separate |
| `plan_execution_started` | Clear the waiting marker and resume execution updates |
| `agent_response` | Record the final-response cursor; do not immediately deliver externally |
| `agent_run_completed` | Finalize the card, then deliver the recorded full response or deterministic completion fallback |
| `agent_run_failed` | Finalize the card as `error` |

Unrecognized events make no Slack-visible change. A change is sent only when the rendered presentation fingerprint differs from the last successful version.

## Update Frequency

The card is posted immediately when the run starts. Non-terminal changes are coalesced and sent no more often than once every two seconds. Terminal changes, questions, and approvals bypass that delay.

Only the latest eight meaningful actions remain visible. Completed older actions are removed from the card but remain available in the Codevil Session activity log.

This rate reduces Slack API pressure and avoids turning token-level activity into visible flicker. Slack `Retry-After` and the existing bounded retry classification remain authoritative when the API rate-limits Codevil.

## Final-Response Ordering

Codevil currently emits `agent_response` before `agent_run_completed`. For Slack-linked runs, the live-card coordinator changes only external delivery behavior:

- the `agent_response` event is still recorded and broadcast to Codevil clients normally;
- its Slack delivery is held by run ID;
- `agent_run_completed` first triggers the terminal card update; and
- after that update succeeds, Codevil sends the existing rendered response chunks in order.

If a successful execution path has no `agent_response` event, Codevil posts a deterministic completion message derived only from the terminal event, such as `Completed. Draft PR: <url>`. It does not synthesize another model response.

If the terminal card update exhausts its immediate retries, Codevil still delivers the final response so a presentation failure cannot hide completed work. The pending card update remains durable and is retried by the coordinator's recovery path.

This behavior applies only to an external destination using live run presentations. Web clients and Sessions without an external destination are unchanged.

## Error Handling and Compatibility

- If initial `task_card` publication fails with an unsupported or invalid-block response, Codevil falls back to a plain in-thread “Codevil is working” message and preserves final-response delivery.
- Transient Slack failures use the existing bounded retry and `Retry-After` behavior.
- A failed intermediate update leaves the last successful card visible and marks a newer cursor pending.
- A failed terminal update never suppresses the full final response.
- Duplicate event delivery converges on the same `run_id`, cursor, message timestamp, and render fingerprint.
- If no external Session link exists, the projector performs no Slack work.
- Existing Slack question rendering and interaction handling remain unchanged.
- Existing non-Slack notification boundaries remain provider-neutral and receive no Slack block types.

Failures and retries are logged with Session ID, run ID, cursor, provider, delivery phase, attempt, status/error code, and retry delay. Logs do not include prompts, final responses, tool arguments, tool results, or Slack message bodies.

## Security and Content Boundaries

The live card is a public projection, not a raw trace viewer.

- Projection starts from validated, redacted Codevil events.
- Only explicitly supported event fields enter the presentation.
- Tool names map through a fixed safe category table.
- Tool arguments and results are not shown in v0.
- User-visible status text is bounded and redacted again before Slack rendering.
- URLs are limited to Codevil's generated Session URL and the validated pull-request URL already emitted by the Agent Run.
- Slack payloads never contain tokens, environment variables, proxy credentials, or full command output.

## Testing

### Projection tests

- Every supported event produces the expected phase, action, waiting, or terminal state.
- Unsupported events and raw thinking deltas produce no card content.
- Tool start/end events converge by call ID and never expose arguments or results.
- Action history is capped at eight entries.
- Secrets and oversized status text are redacted or bounded.

### Slack rendering tests

- Running, waiting, complete, and error projections produce valid `task_card` payloads.
- Every update gets a new `block_id`.
- Accessible fallback text describes the current state.
- **Open session** is always present and **View pull request** appears only with a valid PR URL.
- An invalid/unsupported card response falls back safely.

### Coordinator tests

- Exactly one card is created for each `run_id`.
- Concurrent events produce serialized, monotonically newer card updates.
- Identical render fingerprints do not call Slack again.
- Updates are coalesced within the two-second window.
- Questions and approvals update the card immediately while retaining their existing separate messages.
- A successful run finalizes the card before sending every final-response chunk or the deterministic completion fallback.
- Exhausted terminal-card retries do not suppress the final response.
- Restart recovery retries a projected cursor newer than the delivered cursor without creating a second card.
- Slack retries and duplicated Codevil events remain idempotent.

### Regression verification

- Existing Slack rendering, interactive-question, signature, route, retry, and dedupe tests continue to pass.
- Shared and Worker type checks pass.
- The full repository verification command passes before publication.

## v0 Rollout and Iteration

The change requires a normal Worker source deployment. It requires no new Slack scope, Slack app reinstall, or D1 migration. The new Durable Object SQLite table is added by incrementing Codevil's existing per-Session schema migration version.

After deployment, validate with one fresh tagged Slack request that performs at least a search, edit, test, and successful completion. Confirm:

- the card appears immediately;
- it stays as one message;
- actions are understandable without leaking raw inputs or output;
- question/approval behavior remains usable when exercised;
- the completed card appears before the full response; and
- the PR and Session links work.

Iteration should be driven by this observed workflow. Token-by-token response streaming, cancel/retry buttons, expanded tool detail, direct Codevil diff links, multi-provider live cards, and a Slack Agent/Assistant surface are explicitly deferred beyond v0.
